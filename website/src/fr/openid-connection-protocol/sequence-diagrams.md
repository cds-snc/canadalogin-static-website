# Sequence diagrams

This page presents the sequence diagrams of a login and logout of GC Sign-in.

**GC Sign-in sequence diagram**

This sequence diagram details the interactions between the user, GC Sign-in, and the service provider. It details the following mechanisms:

- retrieving configuration data via discovery url;
- recovery of GC Sign-in public signature keys;
- verification of the signature of tokens by the service provider;

## Details on retrieving information

### Retrieving the GC Sign-in configuration

Retrieving GC Sign-in metadata is optional but allows you to dynamically retrieve the entire configuration, including URLs exposing the signing keys and algorithms used. It is always possible to manually specify the GC Sign-in configuration, regularly ensuring that this configuration has not changed. It is strongly recommended to use dynamic metadata retrieval.

Retrieving metadata via the discovery urlis not mandatory for every connection but must be done regularly. Since these can change, it is necessary for the service provider to ensure that they have the correct data.

### Recovering public signing keys

The service provider is not required to retrieve the GC Sign-in public signing keys for each call. Since these keys change regularly, the service provider must regularly request them again to ensure that they always have valid public signing keys.

### Retrieving the pivot identity during the login senario

Retrieving the pivot identity (UserInfo) must be done immediately after the previous calls (authentication and code retrieval). The validity period of an access_token is 30 seconds.?? 30 seconds to be confirmed by team.

It is not possible to call resources requiring the access_token outside of this timeout.

1. Upstream of the kinematics, the service provider retrieves the CanadaLogin configuration via the discovery url
2. CanadaLogin returns its configuration
3. After the user clicks on the CanadaLogin button, the user is redirected to CanadaLogin on the URL /authorize
4. After authenticating, CanadaLogin redirects the user to the service provider
5. The user returns to the service provider's post login redirect uri
6. The service provider calls CanadaLogin to retrieve the ID Token
7. CanadaLogin returns the signed ID Token
8. The service provider asks CanadaLogin for its public signature keys
9. CanadaLogin returns its public signature keys
10. The service provider verifies the signature of the ID Token
11. The service provider asks CanadaLogin for the /UserInfo
12. CanadaLogin returns the signed UserInfo
13. The service provider asks CanadaLogin for its public signature keys
14. CanadaLogin returns its public signature keys
15. The service provider verifies the signature of the UserInfo
16. The service provider returns the requested page to the user and is authenticated
17. Later, the user disconnects from the service provider
18. The service provider redirects the user to the CanadaLogin logout page
19. The user requests the CanadaLogin logout page
20. Once disconnected from their identity provider and from CanadaLogin, CanadaLogin redirects the user to the post_logout_redirect_uri
21. The user is redirected to the service provider's post_logout_redirect_uri

As a reminder, the OpenID Connect protocol defines the following actors: User, Relying Party and OpenID Provider.
